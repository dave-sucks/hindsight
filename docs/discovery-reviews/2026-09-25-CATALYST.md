## The verdict in three lines

well, caught two of my own tool's mistakes, and correctly pushed back on my prompt. Then it
dispatched five names, told the operator *"all five dispatched … results land on the

filing — every "read the filing first" instruction in every prompt we own is unexecutable.

ones.** That is the honest division of labour, and it matches the August finding exactly.

**Two causes, both mechanical:**
1. **Every writer's first answer was refused** — all four wrote a conviction note over the
   400-character limit, and two invented a trigger kind. The refusal told each one exactly
   what to fix.
2. **Three never got to fix it.** The writer's web search runs its own code sandbox, and the
   model also calls that sandbox (`code_execution`) directly — to count days, to write its
   note to a file. The app doesn't list that tool, so the AI library answers the stray call
   with an error. The call is marked as Anthropic-run, so the library's "did every call get
   an answer" count comes out unequal (`ai@6.0.116`, `clientToolOutputs.length ===
   clientToolCalls.length`) and it ends the loop. The refusal sits unread as the last
   message. EXEL's refusal step had no stray call, so it got its second turn and passed.
   The writer's existing save-retry (`resubmitAfterRefusal`) only runs when the *save*
   refuses an accepted decision — not when the *check* refuses and the loop has ended.
   **→ DAV-313.**

## Defects — tech

**T1. Four of five writers failed and nothing said so.** Causes in the table above: a
400-character limit that refused every first answer, an invented trigger kind, and a
library rule that ended three loops before the writer could read its refusal. Separately,
the chat never found out: `wait_for_thesis_refresh` works on any writer run but describes
itself as for `mode: "refresh"` only, and on a failure it says "FAILED" with no reason —
the refusal is only in the writer's saved thread. Dispatch is fire-and-forget from the
operator's seat. **→ DAV-313 (Agents lane).**

**T2. The agent cannot read a filing.** `get_sec_filings` returns date, form, item codes,
tier and a link. No tool returns a document's text; the chat cannot open a link. So when
Message 2 said *"read the filing it came from,"* the only thing the agent could read was the
calendar's one-sentence quote plus `get_stock_data`'s profile and three news items. It then
wrote *"All classification read directly from filings — no guesses."* **→ DAV-314 (Signals
lane): expose the reader that `catalyst-calendar.ts` already has.**

**T3. The calendar goes stale three ways.**
- *A moved date in different words.* EXEL's Sep 11 8-K: *"the updated Prescription Drug
  User Fee Act action date is March 3, 2027."* None of the three search phrases match that
  wording, so the tool showed Dec 3 and the chat classified *"Dec 3 is the post-extension
  date"* — backwards. The writer, reading the actual filing text, got March 3. Add the
  phrase forms companies use for a move; mark the older date superseded.
- *Early resolution with an 8-K.* SRRK approved Sep 11, filed Sep 14 (item 8.01/7.01). The
  tool still lists Sep 30 as upcoming. Look for "approved" / "complete response letter" in
  later filings.
- *Early resolution with no 8-K.* NUVB approved Sep 16 — no filing at all. EDGAR cannot see
  it. Needs a second source (Drugs@FDA / openFDA) or an explicit "confirm it hasn't already
  happened" step at dispatch. **All three → DAV-314.**

**T4. Keep-in-view rows carry no catalyst date.** SMMT (Nov 14) and COGT (Nov 30) landed
with a price wake and nothing else, so the "N days before the event" review cannot fire on
them. `record_thesis(PASS, status: WATCHING)` should accept and store `catalyst_date`.

**T5. Rate-limited quote mid-session.** PTCT's profile came back *"Live price unavailable
(rate-limited)."* Known; the single Finnhub key is shared. Noted, not new.

## Defects — prompt

**P1. My dispatch gate was wrong** (14–70 days). The chat's correction stands: dispatch on
a primary-sourced date up to ~120 days out; the 14–70 window is the ENTER trigger's job.

**P2. "Read the filing" is an instruction the agent cannot follow** — and it complied by
inventing. Until DAV-314 lands, prompts must say what is actually available: *the
calendar's quote, the filings list with item codes, the profile and news* — and must say
*"if you cannot read the document, say so; never quote it."*

**P3. `DISPATCH_CAP = 5` read as a target, not a ceiling.** Four names cleared the gates.
The prompt said relax only if fewer than three clear. The chat relaxed the single-asset
rule anyway to fill slot 5 with DYN — *"relaxing the single-asset preference for slot 5,
noting it explicitly."* Say *"up to N, and only names that clear"* and drop the cap when
free slots are fewer.

**P4. The Grok cold sweep asked for the wrong thing.** Chat 5's close-out column *"date
confirmed? (yes / doubt / moved)"* and the wide-net framing pulled **nine past events out of
twelve rows** (UNCY, LNTH, OTLK, RARE, IONS, BFRI, SRRK, Elevar, BMY's mega-cap). Zero new
dispatchable names. Grok's value in this session was entirely the *verification* turns —
which is the August finding restated. The cold-sweep prompt needs *"future events only,
from today forward"* in the first line, and the funnel should stop expecting Grok to
originate PDUFA names.

**P5. The session declared itself done before the work landed.** *"Clean. Everything is
recorded."* — with four writers failing in the background. The closing message of any
dispatch session must be a read-back of what exists (`get_theses` on each name), not a
list of what was sent.

## Defects — analysis

**A1. PTCT — a fabricated filing quote.** The chat wrote: *8-K (Sep 21) states: "NDA
resubmission for sepiapterin with a PDUFA date of March 2027."* The filing is about closing
the ST-920 (Fabry) acquisition. Zero occurrences of "sepiapterin", "PDUFA", "resubmission"
or "March 2027" in any of its documents. The quote does not exist. Two external pastes
later said sepiapterin was approved in 2025, and the chat "corrected" a claim it had never
sourced. Root cause is T2; the failure mode is the dangerous one — a confident primary-source
citation that is false.

**A2. EXEL's date and kind were both wrong in the chat**, right in the writer. Chat: *"the
FDA extended … from the original date; the Dec 3 date is the post-extension PDUFA."*
Filing: Dec 3 was the original; the Sep 10 extension moved it to **March 3, 2027**. The
writer's thesis carries March 3 with the 8-K cited. The chat also flipped EXEL's kind twice
(EXTENDED → first approval + extended). Net: the dispatched thesis is correct; the session's
table and the calendar tool were not.

**A3. NUVB was promoted to #1 on a paste, then removed on a paste** — never verified
in-app, because it could not be. The right outcome by luck of paste order.

**A4. DYN dispatched against the seat's own rule** with four names already clear (P3).
Single-asset, first approval, accelerated path on a surrogate — precisely the shape behind
MLTX and MNKD.

**A5. Rankings moved on crowding reads from a scout with "no read" on most names.** BBIO
dropped for HIGH crowding; SMMT was eliminated on it. The scout's crowding column is a
judgement with no stated basis. Fine as a caution flag; it was used as a decider.

**A6. "Triple-source verified" (IBRX)** was one primary quote plus two secondary
restatements of it. Not wrong, but not what the words mean.
