## New Findings

### F1. The narration→execution gate fires DURING the run, not at end

Source: Secular Theme run cmpgvuix1 event-stream trace. Timeline:

```
08:15:52  run_summary  Run Summary — HOLD (6 tickers, 0 traded)   [agent's attempt 1]
08:15:53  run_failed   Narration→execution gap (SMTC EXIT + TRIM) [GATE FIRES]
08:16:09  run_summary  Run Summary — HOLD                          [agent retried summary]
08:16:50  run_summary  Run Summary — HOLD                          [again]
08:17:30  position_closed  Closed LONG SMTC at $146.56 BREAKEVEN  [REAL CLOSE LANDED]
08:17:52  run_summary  Run Summary — ADJUST                        [yet another summary]
08:18:02  position_closed  Closed LONG SMTC at $0.00 BREAKEVEN    [duplicate, $0 reflects a no-op]
08:18:13  run_summary  Run Summary — ADJUST
08:18:34  run_summary  Run Summary — ADJUST                        [4th summary attempt]
```

The gate fires at 08:15:53 based on the FIRST run_summary's narration. The
agent's session continues running past the gate fire because gate-firing
writes a `run_failed` RunEvent but does not abort the underlying
`generateText` / Inngest step. So the agent makes ANOTHER pass, this time
ACTUALLY CALLING `close_position` on SMTC at 08:17:30 — and that real
close_position call ultimately succeeds and reconciles into the
+$108.10 fill at 09:33.

**Implication:** the gate is catching a narration→execution **order**
mismatch (prose first, then tool call), not necessarily a narration
without ANY tool call. The agent self-corrected — it eventually closed
SMTC, just not in the order the gate expected. The run was marked FAILED
even though the close happened.

**This reframes P0-12's fix path.** The gate's diagnostic is correct
("agent narrated close without calling close at that point"), but the
remediation is wrong (mark run FAILED, lose all subsequent work). Better
shapes:
1. **Delay the gate check until end-of-run.** Only fire if the run
   genuinely produces narration-with-no-matching-tool-call across the
   entire session.
2. **Convert the gate to a soft warning + retry.** If the gate fires
   mid-run, write a synthetic system message to the agent ("I noticed you
   narrated 'exit SMTC' without calling close_position — please call the
   tool now") and let the agent continue. If it still doesn't call by
   end-of-run, then FAIL.
3. **Already-executed credit.** If a `close_position` lands AFTER the
   gate fire but BEFORE the run terminates, the gate's verdict should be
   overturned ("agent recovered").

Each of these would also help the Catalyst case: the gate fired both
times, but the agent never recovered (no post-gate close_position
landed). Approaches (1) and (3) would still let Catalyst fail correctly
because the close call never came; approach (2) might give it a chance
to self-correct.

### F4. Secular Theme failed without a retry — divergence from Catalyst's behavior

Catalyst's first failure at 08:03:58 was followed by a fresh Inngest retry
at 08:10:15 (5-minute delay, same shape, also failed). Secular Theme
failed at 08:15:19 and **never retried** — its sole run for the day is
cmpgvuix1, marked FAILED.

This is new: prior days' silent-timeout failures (Earnings Drift 5/11–12,
Secular Theme 5/18, Intraday Momentum 5/19) all triggered cron retries
that recovered cleanly. Today Secular Theme failed via a gate-driven
mark-FAILED (not a silent timeout) and got no retry.

**Hypothesis:** the cron retry path fires on Inngest step failure
(thrown exception, wall-clock timeout) but NOT on a soft FAILED status
that the gate wrote into the run row. The gate's path:
1. record_run_summary preflight detects narration mismatch
2. Writes `RunEvent { type: 'run_failed', ... }`
3. Sets `ResearchRun.status = 'FAILED'`
4. Returns a successful response to the model loop (so Inngest sees the
   step as "OK")
5. Inngest's retry policy doesn't fire because the step technically
   succeeded — the agent self-reported FAILED via DB state, not via an
   Inngest exception

So gate-driven FAILED runs don't get the retry path that silent-failed
runs get. Catalyst's retry MAY actually be the agent itself re-trying via
the existing prematureExitViolation retry inside `morning-research.ts`,
not the Inngest-step retry. **Need to verify in code which retry path
fired for Catalyst.** Either way, the asymmetry between gate-FAILED
behavior (no retry on Secular) and exception-FAILED behavior (retry on
prior days) is worth understanding.

**Fix path:** if P0-12 is being fixed with gate-tightening or
retry-from-rationale shape, the retry should fire consistently regardless
of which gate path triggered. Either the gate THROWS to surface the
failure to Inngest, or the cron explicitly polls for ResearchRun rows
with status=FAILED && retryCount<2 && error includes 'Narration without
tool call'.
