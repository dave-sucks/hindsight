## New Findings

### F1. The V2 prompt is unaware of PENDING (high-severity)

The 2026-05-13 watchlist collapse (PR #265) introduced `direction='PENDING'` for
user/builder/editor-seeded theses. The plan called for:

1. UI/builder/editor mints `Thesis(PENDING, WATCHING, sourceKind='USER_ADDED'|'BUILDER_SEED'|'EDITOR_SEED')`
2. `get_theses.needsAction` surfaces them as `{ kind: 'REVIEW_DUE', pendingFirstReview: true }`
3. The agent calls `update_thesis(thesis_id, direction: 'LONG'|'SHORT'|'PASS', horizon, target_price, stop_loss, entry_price, core_belief, key_assumptions, invalidation_conditions, triggers, rationale)` to promote
4. Tool maps direction='PASS' → status='ARCHIVED' automatically

Steps 1, 2, and 4 work. **Step 3 doesn't, because the V2 prompt
(`buildDailyRunSystemPromptV2`) was never updated with PENDING handling.** I
updated the V1 prompt (`buildV2SystemPrompt`'s Live Theses block) but every
analyst is now on V2.

Today's evidence — Tech Momentum Trader:

```
ticker | direction | type    | summary                          | ts_et
SNDK   | PENDING   | UPDATED | Updated SNDK: rationale updated  | 08:15:30
MU     | PENDING   | UPDATED | Updated MU: rationale updated    | 08:15:22
```

Direction still PENDING. No structural fields set. No triggers attached. No
horizon. Reading the V2 prompt's REVIEW_DUE bullet:

> **REVIEW_DUE** — like a real analyst: re-read the thesis, decide whether the
> world has changed enough to warrant fresh data. ... If the thesis is intact
> and nothing material has happened, `update_thesis` with rationale only — that
> writes a REVIEWED row...

The agent did exactly what the prompt said. There's no "PENDING is a different
shape" branch in the V2 prompt at all.

**This is the test of the watchlist collapse and it failed.** The DB shape is
right, the tool gates are right, but the prompt that drives the agent isn't.

**Fix:** add a PENDING branch to the V2 prompt's per-`needsAction` action map.
Specifically: when `needsAction.kind === 'REVIEW_DUE'` AND `direction === 'PENDING'`
(equivalently: when `pendingFirstReview === true`), the action is `update_thesis`
WITH `direction` set, full structural fields, NOT a rationale-only review. This
is at lib/agent/system-prompt.ts:829 (Step 2 of the "Each morning:" block).

### F2. Earnings Drift INVALIDATED an ACTIVE position's thesis (medium-severity)

TSM was LONG/ACTIVE on Earnings Drift Trader (7.26 sh @ $413.41, opened
2026-05-08, 6 days held). At 08:05:28 today, the morning run fired
`update_thesis(thesis_id, change_status: 'INVALIDATED')` on the TSM thesis. No
matching `close_position` call. The position is still OPEN.

The agent decided the TSM thesis was broken (which is fine) but didn't close
the position (which isn't). The thesis-position pair is now decoupled — same
bug class as yesterday's GOOGL, with the polarity inverted.

The V2 prompt's INVALIDATED instruction doesn't pair it with close_position:

> `update_thesis(change_status: "INVALIDATED", invalid_reason: "<concrete reason>")`
> when the thesis is no longer applicable AT ALL...

But it doesn't say "if there's an OPEN position on this ticker, the close_position
call is also required." That's the gap.

**Fix paths:**
- (a) Tool-side: `update_thesis(change_status: 'INVALIDATED')` on an ACTIVE
  thesis that has a paired OPEN position should reject unless `close_position`
  was called in the same run.
- (b) Prompt-side: pair the INVALIDATED instruction with close_position when
  status was ACTIVE.

(a) is cleaner per the three-layer principle. I'd add it to update_thesis.
