## New Findings

### F1. Phantom `update_thesis(change_status=CLOSED)` writes detached from `close_position`

Earnings Drift's failed run wrote 4 audit rows of type `CLOSED` (NVDA, MU,
ASML, AMD). The tool stats show only 2 `close_position` calls. So 2 of those
4 CLOSED rows were written by `update_thesis(change_status=CLOSED)` — i.e.,
the agent flipped the *thesis* status to CLOSED without calling the *position*
close. NVDA and MU appear to be the real closes (matched `position_closed`
RunEvent rows). AMD and ASML are the phantom ones — at the time the audit
rows landed (~12:03 ET), the AMD position was still OPEN (Tech Momentum
closed it via STOP at 09:37 ET, about 90 min later). ASML may already have
been closed via a prior path; need to verify.

**Risk:** The opposite polarity of the GOOGL desync (P0-10) — that one was
"thesis WATCHING + position OPEN"; this one is "thesis CLOSED + position
OPEN." Both are coherence violations between the structured thesis state
and the actual Alpaca position. The 2026-05-13 zombie-position guard in
`update-thesis.ts` (PR #269) seems to only cover INVALIDATED + ARCHIVED on
ACTIVE-with-OPEN-position; it apparently does NOT extend to `change_status='CLOSED'`
on the same shape. Should the guard fire on `change_status='CLOSED'` too,
or should `change_status='CLOSED'` be reserved for the post-`close_position`
audit path (i.e., never allow the agent to call it directly)?

The cleanest fix matches yesterday's open question on PR #269: extend the
guard to every terminal status change against an ACTIVE thesis with an
OPEN paired position. Today AMD healed by accident (Tech Momentum's STOP
closed the position before EOD). Tomorrow's variant might not heal.

### F3. 0 of 33 tactical fires changed state — noise trigger pattern at full volume

Every tactical run today wrote 2 audit rows (TRIGGER_FIRED + REVIEWED) and
flipped no status. Of the 33:
- 31 were REVIEW_DATE_HIT — the "scheduled review overdue" predicate. Each
  produced a REVIEWED rationale-only update. Not a noise trigger; this is
  the maintenance review pulling the cadence up. But it's *also not the
  vision*: those reviews could have been batched into a single daily run
  for the analyst.
- 2 were PRICE_ABOVE ENTERs (AVGO, MDB) — neither produced a `place_trade`.
  AVGO was already held by the analyst; MDB the agent passed on.
- 1 was PRICE_BELOW REVIEW (NIO, EV Catalyst) — produced REVIEWED only.

**Stage B pain point:** if "trigger fires" overwhelmingly produce just
REVIEW writes with no state change, the trigger system is delivering
visibility, not decisions. The vision says ACTIVE long-term holds get
reviewed monthly OR on trigger fire (big news, big move); the REVIEW_DATE_HIT
trigger is the monthly path, not the big-news path. We need a way to
distinguish "I fired you because the calendar said review" from "I fired
you because something material changed." Today they look identical from
the audit log.

### F4. Tactical-fire / daily-run overlap on Tech Momentum's 5 REVIEWED-rationale-only tickers

Tech Momentum's morning run touched 13 theses including REVIEWED-rationale-only
writes on TSEM, RNG, DELL, NTAP, MRVL. Within ~30 minutes after the morning
run finished, the tactical system fired REVIEW_DATE_HIT triggers on the
exact same tickers and wrote 2 audit rows each. So those 5 tickers got 2
REVIEW audits from the daily run and 2 more from tactical, ~30 min apart.

Two possible interpretations:
1. **Trigger eval doesn't suppress on recent daily-run touch.** The trigger
   evaluator should know "this thesis just got a REVIEWED audit from a
   daily run 5 min ago; suppress the tactical fire." Today it doesn't.
2. **Daily run touched too many.** If the daily run had stayed in its
   focus range (3–4 names), the other 9–10 would have been *correctly*
   handled by tactical. The 92.9% touch ratio means daily is reaching past
   its lane.

Both are real. Stage B should pick the cleaner one to fix first.

## Open Questions

1. **Should the trigger evaluator suppress on recent daily-run touch?**
   5 of Tech Momentum's tickers got 2 daily-run audit rows AND 2 tactical
   audit rows for the same REVIEW_DATE_HIT predicate, ~30 min apart. Read
   `lib/inngest/functions/trigger-evaluator.ts` for the de-dup logic; if
   it doesn't check "thesis had any ThesisUpdate row in the last N
   minutes," that's a one-line add and removes the bulk of today's tactical
   noise.

2. **Why did 0 of 33 tactical runs produce a state change?** Plausible
   reasons: (a) by design — REVIEW_DATE_HIT is meant to write a REVIEWED
   row and update `nextReviewAt`, full stop; (b) the tactical prompt's
   conservatism is too high relative to the daily run; (c) the agent is
   correctly deciding "no material change since last review." If (a), the
   trigger system is delivering visibility-without-decisions and we
   should think about whether that's the right design. If (c), great —
   but then the daily-run touches on those same 5 tickers shouldn't have
   produced rationale rewrites either.

3. **MDB ENTER trigger fired but no trade placed — noise or correct skip?**
   Catalyst Event Raider's MDB tactical run got a `PRICE_ABOVE` ENTER fire,
   ran 35s, wrote 2 audit rows, and did not call `place_trade`. The setup
   may have deteriorated by the time tactical ran (price-pulled-back) or
   the analyst already had exposure. Check the run's audit rationale.

4. **Does PR #269's zombie-position guard cover `change_status='CLOSED'`
   on an ACTIVE thesis with an OPEN position?** Earnings Drift's failed
   run wrote `update_thesis(AMD: ACTIVE → CLOSED)` while the AMD position
   was OPEN (Tech Momentum closed it 90 min later via STOP). The guard
   from PR #269 should have refused that write but apparently did not.
   Read `lib/agent/tools/update-thesis.ts` — confirm the guard set, and
   extend if missing.

5. **Should P1-12 be re-scoped from "Earnings Drift silent timeout" to
   "Cross-analyst silent timeout, retry path is the mitigation"?** Today's
   Secular Theme silence is the second analyst hit. The retry path
   recovered both today's instance and (in retrospect) the 2026-05-12
   instance. Either close P1-12 as "mitigated by retry" or escalate it
   with instrumentation work to count occurrences.

6. **How big is the focus problem when the action mix is heavy purges?**
   Tech Momentum at 92.9% looks bad on the focus heuristic, but 6 of those
   13 touches were data-justified INVALIDATEs and 2 were disciplined
   STOPs. The metric needs a denominator that distinguishes substantive
   actions (state changes, position closes, trade decisions) from
   maintenance writes (REVIEWED rationale-only). Proposal: track two
   ratios — *touched / book* (raw focus) and *decisions / touched*
   (decision density). Today's Tech Momentum: 92.9% / 8 decisions of 13
   touches = 62% decision density. That's a respectable purge, not a
   walk. Re-run on tomorrow's data.

7. **Will any of the 38 fresh-discovery WATCHING theses produce a trade
   this week?** The 4 closes today emptied four positions. New entries
   would need ENTER triggers to fire on the freshly-minted WATCHINGs.
   Track the trade-flow column for 2026-05-19 through 2026-05-22.

  FROM "ResearchRun" r

  WHERE r.mode = 'MORNING_PLAN'

  WHERE ac."enabled" = true
  GROUP BY ac.id, ac.name
)
SELECT ab.analyst, ab.active_or_watching, ab.active, ab.watching,
       COALESCE(COUNT(DISTINCT tt."thesisId"), 0) AS touched_today,
       ROUND(100.0 * COALESCE(COUNT(DISTINCT tt."thesisId"), 0) / NULLIF(ab.active_or_watching, 0), 1) AS focus_ratio_pct
FROM analyst_books ab
LEFT JOIN touched_theses tt ON tt."agentConfigId" = ab.agent_config_id
GROUP BY ab.analyst, ab.active_or_watching, ab.active, ab.watching
ORDER BY ab.analyst;

-- Per-analyst thesis-update breakdown (what was touched, what state changed)
WITH today_morning_runs AS (
  SELECT r.id AS run_id, ac.name AS analyst
  FROM "ResearchRun" r
  JOIN "AgentConfig" ac ON ac.id = r."agentConfigId"
  WHERE r.mode = 'MORNING_PLAN'
    AND (r."startedAt" AT TIME ZONE 'UTC' AT TIME ZONE 'America/New_York')::date = DATE '2026-05-18'
)
SELECT tmr.analyst, t.ticker, t.direction, t.status AS thesis_status, tu.type,
       LEFT(tu.summary, 80) AS summary,
       (tu."fieldChanges"::jsonb ? 'status') AS status_changed
FROM today_morning_runs tmr
JOIN "ThesisUpdate" tu ON tu."runId" = tmr.run_id
JOIN "Thesis" t ON t.id = tu."thesisId"
ORDER BY tmr.analyst, tu.timestamp, t.ticker;

-- Tactical runs: did each one produce any ThesisUpdate state change?
WITH today_tactical AS (
  SELECT r.id AS run_id, ac.name AS analyst,
         r.parameters->>'ticker' AS ticker,
         r.parameters->>'predicateKind' AS pred_kind,
         r.parameters->>'action' AS action, r.status
  FROM "ResearchRun" r
  LEFT JOIN "AgentConfig" ac ON ac.id = r."agentConfigId"
  WHERE r.mode = 'INTRADAY_TACTICAL'
    AND (r."startedAt" AT TIME ZONE 'UTC' AT TIME ZONE 'America/New_York')::date = DATE '2026-05-18'
)
SELECT tt.analyst, tt.ticker, tt.pred_kind, tt.action,
       COALESCE(COUNT(tu.id), 0) AS thesis_updates,
       BOOL_OR(tu."fieldChanges"::jsonb ? 'status') AS status_changed
FROM today_tactical tt
LEFT JOIN "ThesisUpdate" tu ON tu."runId" = tt.run_id
GROUP BY tt.analyst, tt.ticker, tt.pred_kind, tt.action, tt.run_id
ORDER BY tt.analyst, tt.ticker;
