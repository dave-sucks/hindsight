## Findings, ranked by harm

### 1. After the buy wrote PANW's add trigger backwards; it fires at today's close

- **Evidence.** In run `cmwnqr7rx000308l2q71n8ac2`, `edit_triggers` added
  `{watch: "price", is: "below", value: "{priorHigh}", settings: {close: true}}`
  as ADD, set to Send to Agent. Its reason: "If Palo Alto gets back through its
  old high … I would look to add only on that kind of follow-through." Code
  priced the key and saved "Add if below $406.88 · only on the close".
- **Why it's wrong.** PANW is about $360. The condition is true now, so it
  fires at the 16:20 close pass today. That wakes a PANW trigger run with
  `add` on its menu, five hours after the buy. A close below $406.88 never
  makes it false, so it stays spent until the stock closes above $406.88.
  Then a later dip under $406.88 fires it again: the opposite of the
  breakout it meant.
- **Nobody noticed.** The tool echoed back "Add if below $406.88". The
  agent's closing line still said "an add alert on a close through the old
  high".
- **Cause in the code.** `lib/agent/tools/edit-triggers.ts:205-214` fills
  the key and saves it with no look at whether the new trigger is already
  true. The model chose `below`. The tool doesn't say "true now"; the
  reason contradicting the condition is the model's.
- **Fix.**
  - A refusal in `edit_triggers`: for an agent with no trade tools (After the
    buy, the Writer's tailoring), refuse an add or buy that is already true
    at today's price. The refusal says what to do instead: "true at $360 now,
    so it fires at the next check; for 'when it gets back above $406.88',
    use is: above".
  - For other agents, the result line says "true now: fires at the next check".
  - A yardstick case from this fill.
- **Now.** The owner may want to remove or flip this trigger before 16:20.
  This review changed nothing.
- **Roadmap:** E.9 (the After the buy review) for the refusal, E.11 for the
  case.

### 2. "Volume today" is a part-day number shown as the day's

- **Evidence.** The chat (`cmwnorgxo000907jmldpk92up`) at 10:09, 39 minutes
  into the session, called `get_stock_data` on all three stocks:
  - PANW: today 0.73×, yesterday 2.74×.
  - P: today 0.48×, yesterday 2.29×.

  The chat bought PANW on "volume today is 2.74× the 20-day average ✅",
  which was yesterday's bar. It passed on P because "volume today is only
  0.48× … a hard no", which was 39 minutes of trading against a full day's
  average. On a straight-line pace that is about 4.8× a normal day.
  Volume runs heavy early, so the true pace is lower, but it is well above
  the 1.5× bar the chat applied.
- **The pass spread.** The chat's brief told the Writer
  (`cmwnosqeu000h07jmwo3e6w1m`) to "Recommend this be recorded as a PASS:
  volume disqualification is the primary reason". The Writer's data has no
  part-day volume, only "last session 2.29×", so it couldn't check. It
  repeated the 0.48× as "a hard disqualification" and passed.
- **Cause in the code.** `lib/agent/tools/get-stock-data.ts:206-211` divides
  the session's volume so far by the 20-day daily average. `:298` prints it
  as "volume 0.48× normal today", with nothing saying how much of the day
  has gone.
- **Fix.** A fact, not a rule:
  - the field carries the minutes into the session, and a pace (the day so
    far scaled to a full session, or against the same minute's average);
  - the line reads "0.48× a full day's average after 39 of 390 minutes".
- **Roadmap:** E.10 (read tools).

### 3. A failed web search reads as "0 results"; the V sale's note rested on it

- **Evidence.** In the V write-up (`cmwnnpwcu000007jmy86hwxm8`) at 09:40,
  `web_search` returned "Found 0 results". The Vercel log at 14:40:34 UTC
  shows `[sonar] Failed to parse response as JSON` on a reply whose first
  headline was "Visa shares pressured by uncertainty over proposed $38
  billion merchant swipe-fee settlement".
- **What the note said.** Without that, the write-up wrote "Today's company
  news was actually positive". It read the drop as "normal weakness in
  financials". It would hold unless, among other things, "a court outcome
  … forces a broad permanent fee cut". That was close to the news it never
  saw.
- **Where the note went.** It became the sale proposal's reason. The owner
  approved the sale over it at 11:01.
- **Cause in the code.** `lib/intelligence/sonar.ts:114-117` catches the
  parse failure and returns `{ signals: [] }`. `lib/agent/tools/web-search.ts:75-91`
  reports that as "Found 0 results". The earlier fix (a bigger reply
  budget, 2026-10-20) didn't stop truncated replies.
- **Fix.** A failed search is an error the agent sees ("the search failed;
  try a shorter query"), never an empty result. Possibly also salvage the
  whole signals from a cut-off reply.
- **Roadmap:** E.10.

### 4. Double Writer runs: three causes in a chain (E.12)

BEEM, CPA and DOYU each got two Writer runs at 08:00–08:04, before the merges.
**The same can happen after them:** none of the code below changed.

1. **The morning job sends a seed's write-up and doesn't wait.**
   - `lib/inngest/functions/morning-research.ts:166-172` sends a Writer for
     every watch with a review clock and no view (`sendAgentWatchWriteups`).
     That was BEEM, CPA and DOYU at 08:00:20.
   - It then starts the analysts at once. The Mergers run started at 08:01:09
     and read all three as "no view yet, review due".
2. **The send only refuses while a Writer is running.**
   - `findInFlightWriter` (`lib/agent/thesis-writer-dispatch.ts:8-29`)
     matches `status: "RUNNING"`, so the run's first three sends were refused.
   - BEEM's Writer finished at 08:02:03. At 08:02:18 the run sent BEEM again.
     The seed was PASSED by then, so the send became new research and minted
     a second PASSED thesis.
3. **The cron's retry starts with no memory.**
   - The main loop ended at 08:02:54. The process check at
     `morning-research.ts:714` saw "only 1 touched" of 3 and retried. The
     seeds the Writer answered don't count as touched.
   - The seeded retry was rejected ("The messages do not match the
     ModelMessage[] schema"), so it ran historyless (`:810-823`). It sent
     DOYU and CPA again at 08:02:59: a second PASSED DOYU, and CPA's third
     look in three minutes.
   - It then tried `update_thesis` on the passed BEEM and DOYU (refused,
     terminal).

**Cost:**
- BEEM and DOYU each hold two PASSED rows minted a minute apart.
- CPA got five agent passes in 90 minutes: two Writers, two morning notes and
  the 09:30 review after the report. Every one says "keep watching".
- The two terminal refusals can't be answered, because nothing lands on a
  PASSED thesis. The Mergers analyst is told about them for 7 days
  (`lib/agent/gate-rejections.ts:233-250`).

**Fix:**
- `dispatch_thesis_research` refuses a stock whose Writer finished in the
  last few hours and returns that result instead ("written 3 minutes ago:
  PASSED; read it with get_theses").
- The cron's retry leaves out stocks a Writer owns. It doesn't run
  historyless after it dispatched, or it gets the seed messages fixed.
- Optionally, the morning job waits for its own Writers before the analysts
  start (they take about 2 minutes).

**For the planned one-off rewrite of the 31 watches:** add the "finished
recently" refusal first, and don't run the rewrite across 08:00–08:10. Only 3
seeds remain and none has a clock, so tomorrow's morning job sends nothing.
The retry path doesn't need the morning job, though.
