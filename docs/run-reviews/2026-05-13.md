## Forensic walkthrough — what actually broke, where

After tracing each failed run end-to-end against the code paths, the four failures are **not** the same shape. PR #261's INVALIDATE-teaching fix does not address any of them — the agent never reaches the prompt path where INVALIDATE matters.

### Bug 1 — Secular Theme + GOOGL: Layer-2 vs Layer-1 criteria mismatch

**The 9-call sequence** (run `cmp40lq05001d04leqv6cgljx`, 08:07–08:08 ET):

| # | Tool | Notes |
|---|---|---|
| 1 | `read_signals` (urgency LOW, limit 10) | |
| 2 | `get_portfolio_context` | |
| 3 | `get_theses` (ACTIVE+WATCHING) | Returned all 7 theses including GOOGL. **`needs_action: null` for GOOGL.** |
| 4 | `get_stock_data` AMD | Picked up AMD because its `needsAction = REVIEW_DUE`. |
| 5 | `update_thesis` AMD | |
| 6 | `get_stock_data` SMCI | |
| 7 | `update_thesis` SMCI | |
| 8 | `record_run_summary` | Promotion gate fired here: *"GOOGL LONG target $370 met @ $385.88: not named in decision_rationale or its ranked-picks reasoning."* Run marked FAILED. |
| 9 | `complete_run` | Agent narrated *"I'll ensure that the GOOGL thesis is prioritized in the next session"* and called complete_run anyway. Status stayed FAILED (atomic transition is a no-op once FAILED is set) but the agent's experience is indistinguishable from a clean run. |

**Why `get_theses` returned `needs_action: null` for GOOGL — the cooldown finding:**

- GOOGL's ENTER trigger: `predicate: PRICE_ABOVE $370`, `cooldownDays: 1`, `lastFiredAt: 2026-05-12T13:02:27Z` (yesterday 09:02 ET).
- [needs-action.ts:178](lib/agent/needs-action.ts:178) calls `shouldFire(trigger, ...)` from [lib/agent/triggers/evaluate.ts](lib/agent/triggers/evaluate.ts).
- At 08:07 ET today, only ~23 hours had elapsed since yesterday's fire — still inside the 1-day cooldown.
- `shouldFire` returns false during cooldown even when the predicate is currently true.
- needs_action = null.

**The promotion gate at [record-run-summary.ts](lib/agent/tools/record-run-summary.ts) does NOT respect cooldown.** It does its own live-price-vs-target check against `getLatestPrices`. At 12:08 UTC GOOGL was $385.88, target $370 → "predicate is met" → gate fires.

**The mismatch:** Layer 2 (`needsAction`) and Layer 1 (promotion gate) ask different questions about the same thesis. The agent walked the book per Layer 2 (correctly skipped GOOGL because cooldown). The gate then blamed it for skipping. The two layers need consistent rules.

(Side observation: the trigger evaluator's cron fired the GOOGL trigger at 09:05 ET — 57 min AFTER the morning run completed. A separate `tactical-run` was spawned at 09:05 and wrote the REVIEWED audit row at 09:05:39 ET. The trigger system DID handle GOOGL correctly; the morning-run gate complained about something the tactical path already covered.)

### Bug 2 — EV Catalyst + TSLA: narration-gate regex false positive

**The 7-call sequence** (run `cmp40j211000w04leu2493j8n`, 08:05 ET):

| # | Tool | Notes |
|---|---|---|
| 1-3 | read_signals / get_portfolio_context / get_theses | |
| 4 | `get_stock_data` TSLA | |
| 5 | `update_thesis` TSLA (thesis `cmoil5tgg002204l2vr7jocmm`) | rationale: *"TSLA's strategic expansions into AI and energy sectors... Aligning the trade plan to..."* |
| 6 | `record_run_summary` | decision_rationale + pick reasoning for TSLA included the word **"Adjusted"** (referring to target/stop **on the thesis**, not the position). Narration gate fired: *"TSLA narrated manage_position ('Adjusted') with no tool call."* Run FAILED. |
| 7 | `complete_run` | |

**The false-positive regex** at [narration-gate.ts:95-99](lib/agent/narration-gate.ts:95):
```
{ pattern: /\badjusted\b/gi, expectedTool: "manage_position", label: "adjust" }
```

`\badjusted\b` matches "adjusted" anywhere — including "adjusted target", "adjusted thesis", "adjusted plan" — all of which are correctly handled by `update_thesis`, not `manage_position`. Per [THESIS_ARCHITECTURE.md §6](docs/THESIS_ARCHITECTURE.md), the `entryPrice` / `targetPrice` / `stopLoss` fields are "Operational state — mutated freely" via `update_thesis`. `manage_position` is for **Position** (qty, trailing stop %, partial close, scale-in) — not Thesis.

The agent did the right thing. The gate misclassified. **EV Catalyst's failure today is a gate bug, not an agent bug.**

### Bug 3 — Intraday Momentum + INTC: three contract holes around place_trade

**The 7-call sequence** (run `cmp40konv001704ledxr258p9`, 08:06 ET):

| # | Tool | Notes |
|---|---|---|
| 1-3 | read_signals / get_portfolio_context / get_theses | |
| 4 | `get_stock_data` INTC | |
| 5 | `place_trade` INTC SHORT @ $120.61, target $116.19, stop $123.02 | **Rejected.** Agent narrated: *"blocked because the current price exceeded the planned stop loss."* The live-price-vs-stop gate in [place-trade.ts](lib/agent/tools/place-trade.ts) caught it correctly (for SHORT, stop $123.02 must be above entry; live price had moved above $123.02 by the time the trade hit). |
| 6 | `place_trade` INTC SHORT @ $125.72, target $121.01, stop $128.24 (re-priced) | **Rejected.** Agent narrated: *"trade placement failed due to an issue with the analyst identifier."* The `analyst_id` arg the agent passed didn't match `ctx.analystId`. |
| 7 | `complete_run` | **No `record_run_summary` was called.** V2 prompt explicitly requires it. |

**Three distinct contract holes:**

- **3a — `analyst_id` is on the agent-visible schema** in [place-trade.ts](lib/agent/tools/place-trade.ts). It should come from `ctx.analystId` only. Exposing it to the agent means the agent can supply a wrong value and get rejected for something the code already knows. Remove from schema, inject from ctx.
- **3b — Error aggregator missed both rejections.** [morning-research.ts:218-235](lib/inngest/functions/morning-research.ts:218) reads `r?.output?.ok === false` to count errors. Both place_trade rejections returned envelopes that the aggregator counted as `errors: 0` (so `toolStats.byTool.place_trade = { count: 2, errors: 0 }`). The result envelope shape from place_trade rejections doesn't match what the aggregator expects. Every silent fail becomes invisible in diagnostic telemetry.
- **3c — `complete_run` accepted with no prior `record_run_summary`.** [complete-run.ts](lib/agent/tools/complete-run.ts) should refuse the call if no `record_run_summary` event was emitted in this run. Today it accepted, and run was marked COMPLETE despite skipping half the V2 closeout contract.

### Bug 4 — Post-run gate has no teeth (the structural one)

This is the across-bugs structural pattern. The sequence inside `record_run_summary` ([record-run-summary.ts](lib/agent/tools/record-run-summary.ts)):

1. Agent calls `record_run_summary` with decision_rationale.
2. Narration-execution gate runs → if mismatch, writes `run_failed` RunEvent + atomically transitions `ResearchRun.status: RUNNING → FAILED`.
3. Promotion gate runs → same thing if missed thesis.
4. Tool returns a **success-shaped result** to the agent.
5. Agent's next turn calls `complete_run`.
6. `complete_run` tries `RUNNING → COMPLETE` atomic transition. Already FAILED → no-op. Run stays FAILED.
7. **But the agent never learns step 6 happened.** Its experience: complete_run succeeded, run is done.

Today's Secular Theme transcript proves this. Turn 8 (after the gate fired): *"The run encountered an issue due to an omission in the decision rationale: GOOGL met entry conditions but was not addressed in the summary... Let's complete the run, acknowledging this oversight, and mark it for rectification in future analysis."* Turn 9: *"The run is complete. I'll ensure that the GOOGL thesis is prioritized in the next session."* The agent read the gate's complaint, acknowledged it, **and walked away.**

**The fix:** move the gate logic from `record_run_summary` (post-run) to `complete_run`'s preflight (Layer-1 rejection). Refuse `RUNNING → COMPLETE` if any triggered WATCHING thesis is unaddressed in this run. Then the agent's `complete_run` call returns `ok: false` with the same gate message, and the agent loop continues until it actually addresses the thesis.

## Open Questions / Action Items

1. **Bug 1 + Bug 4 share a root cause: the gate is in the wrong layer AND uses different rules than the agent's data feed.** Fixing this is the highest-leverage move. Bug 1 alone says "make the rules consistent." Bug 4 alone says "give the gate teeth." Doing both at once: move the gate to `complete_run`'s preflight, have it call the same `shouldFire` logic that `needsAction` uses. Then the agent sees the same view the gate enforces. **One PR can resolve both.**
2. **Bug 2 (narration regex) is a 5-line fix.** Tighten the `\badjusted\b` pattern to only fire when followed by position-management nouns (stop, trail, size, qty). Don't fire on "adjusted target / thesis / plan" — those are update_thesis territory.
3. **Bug 3a/b/c are three small but distinct fixes** in place-trade.ts schema, morning-research.ts aggregator, and complete-run.ts preflight. None depend on each other.
4. **Decide GOOGL's actual state for Secular Theme.** The thesis has been triggered three times now (2026-05-11/12/13) and the analyst hasn't acted. Either (a) it's a legitimate hold and the system should stop nagging — invalidate manually, or (b) it's a real opportunity the analyst should enter on the next trigger fire. Either way, leaving it as-is means the gate will keep failing the run every time it crosses target intraday.

       "closeReason", "closeSource", "realizedPnl"
FROM "Position"
WHERE ("openedAt" AT TIME ZONE 'UTC' AT TIME ZONE 'America/New_York')::date = DATE '2026-05-13'
   OR ("closedAt" AT TIME ZONE 'UTC' AT TIME ZONE 'America/New_York')::date = DATE '2026-05-13';

-- Overdue-review backlog
SELECT
  COUNT(*) FILTER (WHERE status::text IN ('ACTIVE','WATCHING')
                   AND "nextReviewAt" < (NOW() - INTERVAL '7 days')) AS overdue_7d,
  COUNT(*) FILTER (WHERE status::text IN ('ACTIVE','WATCHING')
                   AND "nextReviewAt" < NOW()) AS overdue_any
FROM "Thesis";
