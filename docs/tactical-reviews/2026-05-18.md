## The four bugs in order

### Bug 1 — `get_stock_data.technicals` is null 100% of the time, breaking the volume-confirmation gate

**Severity: blocker for ENTER conversion.** This is what's stopping tactical
from buying.

**Symptom.** `data.technicals` is `null` on every tactical run in the past 14
days (128/128), and on every morning run sampled (10/10 of the most recent
5/15 cohort). Tickers affected include MDB, AVGO, ZS, DELL, NVDA, AMD — i.e.
everything, not just small-cap or ADR names.

**Code path.** `lib/agent/tools/get-stock-data.ts` lines 135-178: builds
`candles` from FMP `historical-price-full` (primary) or Alpaca bars
(fallback). When `candles` ends up empty/null, `technicals` ends up null.
The downstream `volumeRatio` field (line 178) never gets computed.

**Hypothesis.** FMP returning 403 on the legacy plan + the Alpaca fallback not
firing (either because the fallback condition is wrong, the bars endpoint
itself is failing silently, or the `candles.s !== "ok"` guard short-circuits
before the fallback). Need to read lines 130-160 of get-stock-data.ts with
fresh eyes.

**Fix surface area.** Probably one-line in get-stock-data.ts to fix the
fallback chain, or a switch from FMP to Alpaca-bars-as-primary. The data
absolutely exists in Alpaca (we just placed paper trades through it).

**What to verify after fix.** Re-run one of today's failed ENTERs (MDB or ZS)
in a manual tactical re-invocation and confirm `data.technicals.volumeRatio`
comes back non-null with a real number.

### Bug 2 — `complete_run` preflight rejects tactical runs for missing `record_run_summary`, but tactical can't call it

**Severity: cosmetic-but-confusing.** Today every run wasted 2 of its 15
steps on doomed `complete_run` retries. Status still ends COMPLETE via
`tactical-run.ts:515` because `closedOut = (initialUpdate !== null)` is
satisfied by `update_thesis`. So functionally fine — but the agent's
conversation transcripts are full of refusal messages and the agent is being
trained to ignore the gate, which leaks into the daily-run surface too.

**Code path.** `lib/agent/tools/complete-run.ts:34-50` runs preflight on
**every** run with `runId && analystId && !podcastSegmentId`. Mode isn't
checked. `runCompleteRunPreflight` first gate (line 286-300) checks for a
`run_summary` RunEvent row; if missing, returns `no_run_summary`.

**But tactical's allowlist** (`lib/agent/modes.ts:268-283`) does NOT include
`record_run_summary`. So the agent literally cannot fix the violation.

**Fix surface area.** Two options, both Layer-1 (tool-side):

- **(a)** Make the preflight skip `no_run_summary` for `INTRADAY_TACTICAL`
  mode. Tactical is single-thesis; `record_run_summary` isn't its closer.
  Trade off: tactical loses the ranked-picks artifact, but it never produced
  a useful one anyway (it's the wrong shape for a 1-thesis run).
- **(b)** Add `record_run_summary` to tactical's allowlist + teach the
  tactical prompt to emit a 1-thesis summary. Trade off: 1-thesis summaries
  are a degenerate `record_run_summary` payload; the daily-run review never
  reads them.

Recommend (a). It's cleaner per the three-layer principle: Layer-1 (tool)
should know its own contract; tactical and daily-run are different shapes,
so the gate should differ.

### Bug 3 — Every tactical `update_thesis` today is `type=UPDATED`, masking REVIEWED housekeeping

**Severity: hygiene; not blocking.**

**Symptom.** 37 of 37 today are UPDATED. Yesterday (gpt-4o) was 4 UPDATED /
6 REVIEWED. The shift looks like gpt-5.5 being more verbose under the same
prompt: it now fills `reasoning_summary` + `risk_flags` + `next_review_at`
on every closeout, even when nothing structural changed. The tool sees a
non-empty patch and writes UPDATED instead of REVIEWED
(`update-thesis.ts:825-826`).

**Why it matters.** The `update_thesis` audit log is the only durable record
of what tactical did with its day. If every entry is UPDATED, we lose the
ability to distinguish "the agent rewrote the rationale on a housekeeping
review" from "the agent meaningfully changed the thesis." Search for
`type=REVIEWED` will return nothing for tactical going forward, which makes
the run-review queries less useful.

**Fix surface area.** Two ways:

- **(a) Tool-side:** consider rationale + reasoningSummary + riskFlags +
  nextReviewAt as "narrative only" — if `patch` contains *only* narrative
  keys, classify as REVIEWED. This is the right surface; it's a one-paragraph
  change in `update-thesis.ts:825`.
- **(b) Prompt-side:** tell the tactical agent to call `update_thesis` with
  only `rationale` when nothing structural changed. Less robust — the model
  is being verbose for a reason (it wants to log its reasoning); we'd be
  fighting that.

Recommend (a). The rule "narrative-only patch = REVIEWED, structural-patch =
UPDATED" is what the audit log is supposed to mean.

### Bug 4 — Tactical has never written an ARCHIVED row in 14 days

**Severity: probably correct behavior, worth confirming.**

**Symptom.** `ThesisUpdate.type = 'ARCHIVED'` count from tactical in 14 days:
**0**. Daily-run produces ARCHIVED rows routinely (5 yesterday). Tactical
hasn't.

**Why this might be fine.** The tactical agent's `HARD CONSTRAINTS` section
(intraday-tactical.ts:272-283) says *"You are NOT discovering new names"*
and *"Only $TICKER matters on this run."* Archiving a thesis is a removal
decision typically made in the daily-run portfolio review, not in a
single-thesis trigger response. So 0 ARCHIVED may simply mean "tactical's
role is to act on the existing thesis, not to retire it."

**Why this might be wrong.** The prompt at line 230-237 explicitly allows
`update_thesis(change_status: "INVALIDATED")` when the thesis is structurally
broken. ARCHIVED isn't called out as available. If a tactical run validates
the trigger and concludes the *whole thesis* (not just this trigger fire)
should be dropped, the prompt's only escape valve is INVALIDATED. We've seen
2 INVALIDATED rows from tactical in 14 days (5/08, 5/14) and 0 ARCHIVED. So
the agent IS using the escape valve, just sparingly.

**Recommendation: leave alone for now.** Re-evaluate after Bugs 1+2 are
fixed and we have a few days of tactical actually trading. If a pattern
emerges where the agent INVALIDATES tickers that should have been ARCHIVED
(or vice versa), revisit the prompt's status-flip vocabulary.

## Raw Queries

```sql
-- Tactical run summary, 14 days
SELECT (r."startedAt" AT TIME ZONE 'UTC' AT TIME ZONE 'America/New_York')::date AS day,
       COUNT(*) AS total,
       COUNT(*) FILTER (WHERE r.status = 'COMPLETE') AS ok,
       COUNT(*) FILTER (WHERE r.status = 'FAILED')   AS fail,
       COUNT(*) FILTER (WHERE r.status = 'FAILED' AND r.parameters->>'error' IS NULL) AS silent_fail
FROM "ResearchRun" r
WHERE r.mode = 'INTRADAY_TACTICAL'
  AND r."startedAt" >= NOW() - INTERVAL '14 days'
GROUP BY day ORDER BY day DESC;

-- Predicate × declared-action × outcome conversion (14d)
WITH tr AS (
  SELECT r.id, r.parameters->>'predicateKind' AS predicate,
         r.parameters->>'action' AS declared_action, r.status
  FROM "ResearchRun" r
  WHERE r.mode = 'INTRADAY_TACTICAL'
    AND r."startedAt" >= NOW() - INTERVAL '14 days'
),
acted AS (
  SELECT tr.id,
         BOOL_OR(rm.content LIKE '%"toolName":"place_trade"%')      AS placed,
         BOOL_OR(rm.content LIKE '%"toolName":"close_position"%')   AS closed,
         BOOL_OR(rm.content LIKE '%"toolName":"manage_position"%')  AS managed
  FROM tr JOIN "RunMessage" rm ON rm."runId" = tr.id
  GROUP BY tr.id
)
SELECT tr.predicate, tr.declared_action,
       COUNT(*) AS runs,
       COUNT(*) FILTER (WHERE a.placed)  AS placed,
       COUNT(*) FILTER (WHERE a.closed)  AS closed,
       COUNT(*) FILTER (WHERE a.managed) AS managed,
       COUNT(*) FILTER (WHERE NOT a.placed AND NOT a.closed AND NOT a.managed) AS no_action
FROM tr JOIN acted a ON a.id = tr.id
GROUP BY tr.predicate, tr.declared_action
ORDER BY runs DESC;

-- Null-technicals incidence
WITH tactical_runs AS (
  SELECT r.id FROM "ResearchRun" r
  WHERE r.mode = 'INTRADAY_TACTICAL'
    AND r.status = 'COMPLETE'
    AND r."startedAt" >= NOW() - INTERVAL '14 days'
)
SELECT
  COUNT(*) FILTER (WHERE rm.content LIKE '%"technicals":null%')  AS technicals_null,
  COUNT(*) FILTER (WHERE rm.content LIKE '%"technicals":{%')     AS technicals_present,
  COUNT(*) AS total
FROM tactical_runs tr JOIN "RunMessage" rm ON rm."runId" = tr.id;

-- ThesisUpdate type distribution from tactical (by day)
SELECT (r."startedAt" AT TIME ZONE 'UTC' AT TIME ZONE 'America/New_York')::date AS day,
       COUNT(*) FILTER (WHERE tu.type = 'UPDATED')        AS updated,
       COUNT(*) FILTER (WHERE tu.type = 'REVIEWED')       AS reviewed,
       COUNT(*) FILTER (WHERE tu.type = 'INVALIDATED')    AS invalidated,
       COUNT(*) FILTER (WHERE tu.type = 'STATUS_CHANGED') AS status_changed,
       COUNT(*) FILTER (WHERE tu.type = 'ARCHIVED')       AS archived
FROM "ResearchRun" r JOIN "ThesisUpdate" tu ON tu."runId" = r.id
WHERE r.mode = 'INTRADAY_TACTICAL'
  AND tu.type != 'TRIGGER_FIRED'
  AND r."startedAt" >= NOW() - INTERVAL '14 days'
GROUP BY day ORDER BY day DESC;

-- ENTER → place_trade conversion detail (with already-open-position flag)
WITH tactical_enter AS (
  SELECT r.id AS run_id, r."startedAt", r.parameters->>'ticker' AS ticker,
         ac.id AS analyst_id, ac.name AS analyst,
         r.parameters->>'thesisId' AS thesis_id, r.status
  FROM "ResearchRun" r
  JOIN "AgentConfig" ac ON ac.id = r."agentConfigId"
  WHERE r.mode = 'INTRADAY_TACTICAL'
    AND r.parameters->>'action' = 'ENTER'
    AND r."startedAt" >= NOW() - INTERVAL '14 days'
),
trade_calls AS (
  SELECT te.run_id, te.ticker, te.analyst,
         COUNT(*) FILTER (WHERE rm.content LIKE '%"toolName":"place_trade"%') AS place_trade_calls
  FROM tactical_enter te
  LEFT JOIN "RunMessage" rm ON rm."runId" = te.run_id
  GROUP BY te.run_id, te.ticker, te.analyst
)
SELECT te.analyst, te.ticker,
       (te."startedAt" AT TIME ZONE 'UTC' AT TIME ZONE 'America/New_York')::timestamp(0) AS started_et,
       tc.place_trade_calls, te.status,
       (SELECT p.status FROM "Position" p
        WHERE p.symbol = te.ticker AND p."analystId" = te.analyst_id
          AND p."openedAt" < te."startedAt"
          AND p.status = 'OPEN'
        LIMIT 1) AS preexisting_open_position
FROM tactical_enter te
JOIN trade_calls tc ON tc.run_id = te.run_id
ORDER BY te."startedAt" DESC;
```
